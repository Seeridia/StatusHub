# 故障排查

[返回操作文档](README.md)

## 页面打不开或 8080 被占用

1. 确认 `statusmon-api` 的终端仍在运行；Compose 不负责启动它。
2. 检查 `/healthz`、`/readyz`，再检查数据库/NATS 容器状态。
3. 如提示端口占用，在 macOS/Linux 安装有 lsof 时执行 `lsof -nP -iTCP:8080 -sTCP:LISTEN`，确认已有进程身份。
4. 需要重启时到原终端 Ctrl-C，避免凭进程名称批量终止不相关服务。

## 登录失败、没有编辑按钮

| 现象 | 检查与处理 |
| --- | --- |
| 401 或“凭据无效” | 工作区 slug 与 token 是否属于同一租户；是否复制完整 `sa.` 令牌；是否有空格 |
| 能查看但不能添加 | 当前角色是否 viewer；切换到 operator 或更高的既有账号 |
| 使用服务账号名称作为密码失败 | 名称不是凭据，使用创建结果中的 `token` |
| 邮箱密码登录失败 | 检查邮箱验证、密码、工作区成员启用状态；使用忘记密码流程恢复 |
| SSO 失败 | public URL、redirect URI、issuer、client ID、邮箱域及 issuer/subject 绑定 |
| 重启后 cookie/SSE cursor 失效 | 是否更换了 `STATUSMON_API_KEY`；恢复原配置后重新登录 |
| 403 | 先区分角色权限不足与 cookie 写入缺少 CSRF，不要关闭认证来排错 |

退出登录不会撤销服务令牌。如果令牌丢失或泄露，请有权限的管理员在「设置 → 服务账号」停用或轮换，详见 [团队账号](team-accounts.md)。

## 网页仍是演示数据或更新后外观没变

- URL 中 `?demo=1` 表示 Vite 开发演示，正常入口使用 `/ui/?tenant=local`。
- 数据库中的 `Gatus Demo`、`Cachet Demo` 等可能是真实抓取的公开测试站点，名称带 Demo 不代表网页正在使用内置假数据。
- 修改前端后按“`make ui-build` → 重编译/重启 API → 刷新网页”的顺序操作。已经启动的 Go 二进制不会自动读取新构建资源。
- Vite 5173 在真实模式下仍需 8080 API；只启动 Vite 不会获得真实事件。

## 状态页检测失败

1. 在浏览器确认提交的公开 HTTPS 地址能访问；不要输入后台管理地址或需登录的页面。
2. 记录 URL、错误时间、API 返回摘要及脱敏日志。不要只截最后一句“请求失败”。
3. 区分 DNS/网络超时、非预期 HTTP 响应、SSRF/IP 限制、API schema 变化与尚未支持的引擎。
4. 探测与创建有超时限制。临时网络故障可稍后重试；持续不支持的站点需要新增/修订适配器或受控 HTML recipe。
5. 不要通过关闭证书校验、DNS pinning 或 SSRF 检查来“修复”探测。

若提示已经接入，直接复用现有来源，不要使用变体 URL 人为创建多份。

## 添加成功却没有新数据

先查看 `statusmond` 日志和数据源的 `enabled`、`next_poll_at`、`last_attempt_at`、`last_success_at`、`failure_streak`：

- `last_attempt_at` 不推进：worker 未运行、来源未到调度时间、租约未释放，或区域 ownership 不匹配。
- 尝试时间推进但成功时间不推进：网络、认证、解析或上游错误。
- 成功时间推进但没有事件：可能没有事故，也可能该适配器只支持部分资源；核对探测结果。
- 老版本升级后仍无组件/事件：确认正在运行的 worker 包含快照到查询表的事务同步，而不是只更新 checkpoint 的旧版本。

不要直接清空 checkpoint、canonical events 或租约表来“强制刷新”；这会改变幂等/基线语义。租约和区域问题按 [高级运维](../advanced-operations.md) 排查。

## 明明刚采集，为什么事件很旧

成功采集时间代表这次请求成功；事故时间来自上游。一些来源会持续返回很久以前未结束的记录，或只提供有限历史窗口。请核对“厂商更新时间”和处理阶段，不要把“系统发现时间”当成新发生事故的证明。

采集健康与厂商服务健康独立显示；采集失败应表现为过期/采集异常，不能被解释为厂商业务宕机。

## 渠道测试失败或一直等待

- 测试由 API 内的 endpoint-test worker 执行，API 是否还在运行？
- HTTPS 地址和凭据是否完整，目标接收端是否允许该请求？
- 是否出现 429、鉴权错误、证书/DNS 问题或禁止重定向？
- API 是否能使用原 `STATUSMON_CONFIG_KEY` 解密配置？
- 等待中的 job 是否仍有有效租约？先查看日志及最终状态，避免连续创建测试任务。

测试会发送真实消息。地址、签名密钥或 Slack Webhook 应在接收端确认，不要把它们贴到公共日志中。

## 测试成功，但真实通知没有到达

按顺序检查：

1. `statusmond` 持续运行，且 API/worker 的加密 key 和 key ID 一致。
2. 规则和渠道启用，规则确实关联了这个渠道。
3. 创建规则之后产生了新的 canonical event；首次基线不补发历史事故。
4. 厂商、事件类型、最低影响、关键词和静默时段是否把事件过滤掉。
5. 投递记录是否创建：没有则检查事件/匹配链路；有则检查 attempts、返回码、退避或死信。
6. 接收端是否接受并继续处理；“渠道接受”不等于接收人阅读。

恢复通知被过滤时，特别检查最低影响阈值。不要反复复制规则来绕过排查，这可能造成重复通知。

## SSE 反复重连

检查 `/readyz`、NATS 连接、API 日志以及代理缓冲/超时。网页会自动退避重连，暂时重连不代表数据库中事件丢失。API key 改变会使旧签名游标失效，必要时恢复原 key 并重新登录。

## 迁移提示“表已存在”

`make migrate-up` 没有自动识别已执行迁移。停止重跑，检查 schema 和升级记录，只执行已确认缺失的迁移。不要执行 `make migrate-down` 或删除数据库绕过错误。详见[版本升级](maintenance.md#版本升级)。

## 配置解密失败

API 和 worker 必须使用创建渠道时相同的配置 key/key ID。不要重新随机生成一个 key 期待解密旧数据。优先从受控备份恢复原 key；原 key 无法恢复时，需要有计划地重建受影响配置，数据库备份本身不能还原密钥。

## 界面遮挡、异常滚动或按钮不可见

1. 记录页面地址（移除敏感参数）、窗口宽度、主题和截图。
2. 确认已刷新到最新构建，重置浏览器临时缩放后复核。
3. 宽表格允许内部横向滚动，右侧列不一定在当前视口内。
4. 无权限按钮隐藏属于角色限制；真正的遮挡应附上被遮挡元素、期望行为和操作步骤。

## 提交问题前收集

提供版本/提交标识、发生时间与时区、相关页面、最短复现步骤、脱敏错误摘要、健康检查结果，以及必要的来源/事件/投递 ID。不要附上 `.env`、服务令牌、Webhook URL 中的凭据、完整数据库备份或未脱敏 HTTP headers。
